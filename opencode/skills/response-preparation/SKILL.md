# Response Preparation

This skill decides what belongs in a report. How the sentences are written belongs to
[[writing/technical-copy/technical-copy|technical copy]].

Read [references/process-narration.md](references/process-narration.md) first. It owns
the failure that produces most corrections here: stopping work to describe it,
manufacturing blockers and decisions, and flagging instead of acting. Read
[references/coherence-check.md](references/coherence-check.md) before sending: it catches
a statement that is wrong or alarming while reading as routine status.

## Success is the expected outcome

State the result in a sentence. Give the rest of the report to gaps, blockers, surprises,
decisions, and incomplete required work. Include verification or a causal account only
when the user asked for it, when it substantiates the result, or when it changes what
happens next.

## Continue before reporting

If safe in-scope work remains on the assigned request, do it. A progress report is not a
substitute for that work. This does not authorize newly discovered work outside the
request.

## Keep in-scope obligations visible

Name unfinished work that remains part of the active request. Do not relabel it as
optional because a local subtask succeeded. Work discovered outside the request is a
finding, not authorization.

## Labels must mean what they say

Re-read every labeled section of the draft. "Remaining" holds work not yet done.
"Open items" holds items still unresolved. "Completed" holds things that were done.
A section whose content contradicts its label is worse than no section. Delete it.

## The synthesis gate

Complete this sentence before sending:

> The user needs to know _____ because it changes _____.

The first blank names a gap, blocker, surprise, divergence, or decision. The second
names the action, expectation, proof burden, or choice it affects. If no such item
exists, give the result and its evidence in a few lines. A chronological account of
completed work never dominates the information that changes what happens next.

## Stay on the requested object

Identify the object the user asked you to judge or transform. A request for a
postmortem, review, or failure analysis is answered with the judgment about the
evidence, not with a summary of the object-level problem inside it. When the evidence is
a correction sequence, the user needs the sequence-level pattern: what each correction
removed, which assumption survived too long, where the frame should have been reset.

## The artifact is positive

A final plan, spec, recommendation, or note states what to do. It does not carry the
history of rejected alternatives or caveats that exist only because earlier turns were
wrong. Keep a negative rule only when it is a durable constraint a future worker must obey.

## What a report contains

Only what the user needs and cannot already see:

- gaps that block the overall task;
- decisions that need user input;
- errors or surprises the user should know about;
- divergences between what was asked and what was done;
- remaining mandatory work in the overall task.
